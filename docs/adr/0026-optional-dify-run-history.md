# ADR 0026 — 可选的 Dify 公共 API 运行历史持久化

## 背景

用户要求继续建设兼具 LangGraph 编排能力与 Dify 应用能力的 Spine 家族，并按需求文档、失败测试、实现的顺序开发。
现有 `service/api/dify_public.py` 把终态运行摘要放在应用进程内的 `OrderedDict`，服务重启后不能查询。
现有编译器、执行安全门与公共 API 可以复用；本次不另造执行器。

完整需求见 [能力 PRD](../prd-langgraph-dify-capabilities.md)，验收见 [测试计划](../test-plan-langgraph-dify.md)。

## 决策

1. 增加可选 `ServiceConfig.dify_public_run_store_path`，对应 `RAGSPINE_DIFY_PUBLIC_RUN_STORE_PATH`。
   未配置时保留现有内存历史行为；配置本地 SQLite 文件时，成功及失败的终态摘要持久化后才能返回正常运行响应。
   blocking 与现有 SSE 回放使用同一存储路径。
2. 使用标准库 SQLite 与短生命周期连接，事务内写入并执行容量清理；不引入新的服务或强制依赖。
   文件模式每个 app-key 归属最多保留 100 项，按写入顺序淘汰；读取不改变顺序。
   默认内存模式的现有容量语义不变。
3. 归属标识使用 API key 的 SHA-256 摘要，查询同时约束归属与 run ID。原始 Bearer key 不写入存储。
   不同有效 key 查询同一 ID 都表现为不存在；相同 YAML 配置不会使两个 key 共享历史。
   key 轮换后旧历史不能通过新 key 查询。这是 app-key 隔离，不是 workspace 或请求 `user` 的权限模型。
4. 保存现有公开摘要字段，包括业务输入、输出与错误；读取时重新验证公开响应模型。
   这些是授权历史数据，不进入隐私 trace。摘要键散列不是业务数据加密，运行目录及备份权限由部署管理。
5. 存储不可用、数据库损坏或摘要结构损坏返回脱敏的 `503 / history_unavailable`，不能静默退回内存或伪装成 404。
   不自动重试工作流。执行完成后存储失败意味着工作流可能已经产生外部副作用，不能据此宣称执行失败或未执行。
6. 测试先证明跨应用实例及跨进程读取、成功/失败/streaming 历史、隔离、容量、损坏和中文路径，再实现。
   保留既有鉴权、执行开关、运行安全门和响应形状回归。

## 明确边界

本次保存的是**终态运行摘要**，不包含执行检查点、待执行节点、断点恢复、实时事件或完整逐节点历史。
进程在执行中或提交前崩溃的运行不在此保证内。SQLite 文件持久化也不构成分布式执行服务。

ADR 0013 的编译模型与 ADR 0014 的安全入口不变。后续通用状态图、检查点及恢复机制应由
`spineagent` 承担，平台工作区及发布生命周期由 `spinestudio` 承担，并在各自实现前另立决策。
ragspine 已有的工作流 Studio 和 DSL 入口继续复用。

## 备选与取舍

- 只保留内存：不满足重启查询要求，因此仅保留为默认兼容路径。
- 复用 n8n JSON 文件库：该库有不同的 ID、容量与损坏跳过语义，不直接套用于此接口。
- 强制 PostgreSQL/Redis：增加离线本地使用成本；当前单机摘要需求无需引入。
- 把终态历史称为 checkpoint：信息不足以恢复执行，拒绝这种契约。

SQLite 以事务提供单机多进程读写一致性；网络文件系统、远程共享数据库、密钥轮换迁移、按时间清理和运行列表接口不属于本切片。
